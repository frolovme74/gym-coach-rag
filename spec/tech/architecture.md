# Архитектура

## Текущее состояние v4

Рабочий профиль — `data/corpus-v4/profile.json`, модель — GigaChat-3-Ultra.
Одна база содержит научные чанки и практические карточки с явным происхождением.
Вопросы проходят BM25 и приоритет правил FAQ (`runtime_retrieval.py`), программы
отбирают карточки по метаданным и проверяются `planner.py`. Обе ветви возвращают
источники из той же базы. Новых зависимостей нет. Сборка:
`python scripts/build_practical_corpus.py`; повторная оценка:
`python -m benchmark.practical_v4 --output /tmp/new-v4-report.json`.
Подробности текущего поведения — `integration.md` и `practical-corpus.md`;
разделы этапов ниже описывают историю реализации.

## Путь запроса

```
Браузер (app/static)
   │  POST /api/ask {question}
   ▼
HTTP-сервер (app/server.py)        — валидация, маршрутизация, JSON
   │
   ▼
Пайплайн RAG (app/rag/pipeline.py) — поиск, генерация, проверка цитат
   │
   ├─► Предобработка (app/rag/preprocess.py) — нормализация, токены, леммы
   ├─► Индекс BM25 (app/rag/bm25.py)         — топ-k фрагментов
   └─► Клиент LLM (app/llm.py)               — ответ по фрагментам
   │
   ▼
Ответ {answer, found, sources[]} → браузер показывает текст и источники
```

При старте сервер загружает профиль v4, корпус `data/corpus-v4/documents.json`
и `data/index/bm25.v4.json`. При отсутствии файла индекс строится в памяти.
Явная сборка: `python scripts/build_practical_corpus.py`.
Подробный контракт — [integration.md](integration.md).

## Принятые решения

Для предобработки используется `pymorphy3` с русским словарём: это разрешённая
заданием морфология, не поисковый индекс и не модель перевода. Зависимости
поискового слоя фиксируются отдельно в `requirements-rag.txt`. Для проверки
создаётся лёгкое окружение `venv/rag`; настоящий сервер требует зависимости поиска.
Анализатор загружается только при вызове
лемматизации, результаты разбора слов кешируются с ограничением размера.

**Python 3.11+ и стандартная библиотека для HTTP-сервера.** `http.server`
достаточно для одной страницы и трёх маршрутов. Поиск требует установки
`requirements-rag.txt`; затем приложение запускается `python -m app`.
Если понадобится потоковая выдача или много маршрутов, рассмотрим FastAPI.

**Интерфейс без сборки.** Обычные HTML, CSS и JavaScript: любой участник может открыть и поправить файл, не нужен Node.js.

**Шрифты с Google Fonts.** Unbounded и Manrope подключаются ссылкой в `index.html` — это единственный внешний ресурс интерфейса. Без сети страница работает на системных шрифтах. Если защита будет проходить без интернета, шрифты нужно положить в `app/static/fonts/`.

**Настоящий пайплайн вместо заглушки.** Сервер всегда возвращает `mode:rag`.
Контракт расширен цитатами, ссылками на оригиналы и отказом от программы;
интерфейс и тесты обновлены вместе с `spec/tech/api.md`.

**Самостоятельный BM25 на стандартной библиотеке.** TF, DF, IDF и ранжирование реализованы в `app/rag/bm25.py`; новых зависимостей нет. Запрос обрабатывается с настройками построенного индекса. Файл JSON проверяется при загрузке; запись атомарно заменяет предыдущий индекс только после успешной сериализации.

**Индекс в памяти, сохраняется в файл.** Корпус небольшой (сотни фрагментов), база данных не нужна. Индекс сериализуется в `data/index/` и в Git не хранится — он воспроизводится из корпуса.

**Автономный подбор параметров.** `benchmark/tune.py` использует существующую
предобработку и собственный BM25. Новых зависимостей нет. Корпус и разметка
фиксируются хешами; параметры и порог выбираются только по тренировочной
части каждого разбиения. Кандидат сохраняется в `benchmark/selected_config.json`
и отдельный `data/index/bm25.tuned.json`; сервер его пока не читает.

**LLM как сменный клиент.** Провайдер и модель задаются через `.env`; пайплайн
зависит от интерфейса `generate(messages, max_tokens=...)`. Провайдер — GigaChat
API, личный Freemium. Авторизация и генерация проверены с реальным ключом.

## Проверка

Подготовка корпуса работает с сохранёнными английскими оригиналами, русскими
переводами и редакторскими решениями. Модули загрузки весов, машинного перевода
и проба Qwen/MLX удалены после завершения экспериментов. Тяжёлых зависимостей
Torch, Transformers, CTranslate2 и MLX в текущей процедуре нет.

Проверки чисел, единиц, пустого текста, повторов и отрицаний вынесены в
`scripts/corpus_quality.py` (стандартная библиотека). Их используют редактура
и тесты. Загрузка/очистка статей, нарезка, редакторская сборка, валидация и
ревизия v3 сохранены. Назначение каждого модуля — `scripts/README.md`.
Результаты прежних переводческих проб остаются данными исследования;
повторный запуск этих моделей больше не поддерживается кодом проекта.

| Что | Как |
|---|---|
| API | `python -m unittest discover -s tests -v` |
| Интерфейс | вручную пройти сценарии из `spec/product/scenarios.md` |
| Поиск | прогон benchmark, метрики в `benchmark/results/` (КТ2) |


## Автономная ревизия v3

- `scripts/corpus_revision.py` воспроизводит адресные правки из old/new-патча в
  отдельный `data/corpus-v3/`, сохраняя ID и происхождение.
- `app/rag/retrieval.py` — адаптер собственного BM25 с симметричными термами
  понятий в документах и запросах; отдельная сериализация с хешем правил.
- `benchmark/compare_retrieval.py` фиксирует входы, сравнивает четыре сочетания
  корпуса/поиска, выбирает вариант только на development и сохраняет отчёт.
- Профиль `benchmark/retrieval-v3/selected_config.json` и индекс
  `data/index/bm25.v3.json` автономны. API, заглушка и LLM не изменены.

132 теста проверяют в том числе распознавание понятий, отрицательные примеры,
сохранение чисел/отрицаний, сериализацию, воспроизведение правок и фиксированные
метки сравнения. Порог отказа новой шкалы не откалиброван.


## Аудит v3.1 и порог v3

`benchmark/audit_v3.py` проверяет строго ограниченное расширение разметки (8 новых
пар и один явный пересмотр), сохраняет прежние решения, подтверждает неизменность
выдачи и подбирает только score-порог на development. Три части проверяют порог
на отложенных вопросах при фиксированном retrieval. Разметка, протокол и новый
профиль находятся в `benchmark/retrieval-v3.1/`; новых зависимостей нет.
Тестов 138; сервер и интеграция не изменены.


## Локальная очистка после подготовки корпуса

20 ноября 2026 по запросу пользователя удалены локальные `data/models/`,
`venv/translation/` и `venv/mlx/`. Это не зависимости работающего поиска.
Сохранены `venv/rag/`, скрипты подготовки, requirements-файлы, исходные
материалы, переводы, корпуса и все результаты benchmark. Для повторного
машинного перевода потребуется заново создать соответствующее окружение,
установить его зависимости и скачать модель. Это состояние до последующей
очистки кода: затем удалены и движки перевода, поэтому для нового машинного
перевода понадобится отдельно вернуть или реализовать соответствующий инструмент.
После очистки все 138 тестов проходят, 118 исходных контрольных сумм и
зафиксированные версии benchmark проверены.


## Проверка после удаления движков перевода

Все 136 актуальных тестов проходят. Два теста удалены вместе с сегментацией
входа для больше не используемых моделей; проверки чисел, единиц, отрицаний,
очистки, редакторских решений и границ чанков сохранены. Валидатор исходного
корпуса проверен без перезаписи результатов, 118 контрольных сумм и протоколы
benchmark совпадают. Ни корпус, ни ранжирование в этой очистке не менялись.


## Клиент GigaChat — первый шаг интеграции

`app/llm.py` предоставляет `GigaChatClient.from_env()` и `generate(messages)`.
Используется стандартная библиотека Python: HTTP, TLS, JSON, .env без выполнения
команд и подстановки переменных. Переменные процесса имеют приоритет над .env.
Новых зависимостей нет. Провайдер GigaChat, scope только GIGACHAT_API_PERS;
модель по умолчанию GigaChat-2-Pro, настраивается через .env. Ключ хранится
в исключённом из Git .env, шаблон без ключа — .env.example.

Authorization key обменивается на access token через официальный OAuth URL;
expires_at читается в миллисекундах, обновление с запасом 60 секунд. Один экземпляр
клиента последовательно выполняет запросы (лимит физлица — один поток). Проверка
TLS включена всегда; дополнительный CA-файл загружается в SSLContext приложения.
Автоматические перенаправления HTTP отключены. Таймаут на сетевую операцию;
для HTTP 429/503 допускается один ограниченный повтор, после 401 у модели —
одно обновление токена. Сетевой таймаут генерации не повторяется автоматически.
Тела ошибок провайдера, ключ и токен не выводятся в сообщения ошибок.

`generate` возвращает текст, модель и usage; обрезанный ответ или blacklist
вызывает отдельную ошибку, а не выдаётся за полный ответ по источникам.
CLI --check проверяет авторизацию/список моделей без генерации; --smoke делает
один небольшой пробный запрос. Реальные вызовы возможны только после настройки
пользователем. Тесты клиента используют подменённый HTTP-транспорт.

На этом шаге сервер, заглушка, RAG-пайплайн и продуктовые промпты не меняются.
Клиент транспорта не обеспечивает сам по себе достоверность, ссылки или
правила медицинских отказов: это следующий шаг пайплайна.
