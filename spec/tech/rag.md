# RAG: поиск и генерация

Статус: проект решения к контрольной точке 2. Код ещё не написан; параметры уточняются по результатам benchmark.

## Корпус и документ

Корпус — материалы на русском языке по четырём областям: тренировки, питание, спортивные добавки, восстановление (см. `spec/product/product.md` и `data/corpus/README.md`). Области представлены сопоставимым числом документов, чтобы ни одна не доминировала в выдаче.

Индекс один на весь корпус: вопросы часто лежат на стыке областей («что есть после тренировки для восстановления»), и разделение на отдельные индексы потеряло бы такие документы.

Материалов о рецептурных препаратах, анаболических стероидах и допинге в корпусе нет — это первая линия защиты от ответов на такие вопросы.

Документ (единица индексации) — фрагмент исходного материала: раздел или несколько абзацев на одну тему, примерно 100–300 слов. Причины:

- в промпт LLM помещается несколько фрагментов целиком;
- источник в интерфейсе — это конкретный кусок текста, который можно прочитать и сверить;
- нормализация по длине в BM25 работает лучше, когда документы сопоставимы по размеру.

У каждого документа есть `doc_id`, область (`training`, `nutrition`, `supplements`, `recovery`), название исходного материала, заголовок раздела и текст. Область в ранжировании не участвует: она нужна для интерфейса, для предупреждения о добавках и для разбивки метрик.

## Предобработка

Одинаковая для документов и запросов.

1. **Нижний регистр.** В корпусе нет терминов, которые различаются только регистром.
2. **Замена «ё» на «е».** В текстах написание непоследовательно.
3. **Токенизация по словам:** последовательности кириллических и латинских букв и цифр, дефис внутри слова сохраняется. Слово — естественная единица для BM25 и для лемматизации; числа сохраняем, потому что они значимы («5 повторений», «3 подхода»). Латиница и дефис нужны для терминов питания и добавок: «BCAA», «омега-3», «B12» должны оставаться одним термом. Латинские токены не лемматизируются.
4. **Лемматизация** библиотекой `pymorphy3`. Русский язык морфологически богат: «подход», «подхода», «подходами» без лемматизации — разные термы, и запрос в одном падеже не найдёт документ с другим. Методические указания разрешают готовую библиотеку лемматизации.
5. **Удаление стоп-слов** (предлоги, союзы, частицы) по короткому собственному списку. IDF и так даёт им малый вес, но удаление уменьшает индекс и шум в коротких запросах.

Влияние шагов 4 и 5 проверяется на benchmark: сравниваем метрики с лемматизацией и без неё, со стоп-словами и без. Результат сравнения записываем сюда.

## Индекс

Реализуется самостоятельно, готовые поисковые индексы не используются.

Структуры данных:

- инвертированный индекс: терм → список пар (`doc_id`, TF);
- длина каждого документа в термах и средняя длина `avgdl`;
- DF каждого терма и число документов `N`.

## Ранжирование

BM25 по формулам из методических указаний:

```
IDF(t) = ln(1 + (N − DF(t) + 0.5) / (DF(t) + 0.5))

BM25(q, d) = Σ по t из q:  IDF(t) · TF(t,d)·(k1 + 1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl))
```

Начальные параметры: `k1 = 1.5`, `b = 0.75`. Подбираются по benchmark.

Документы без единого терма запроса не оцениваются. Выдача — первые `k = 5` документов по убыванию оценки.

## Отказ от ответа

Если ни один документ не набрал оценку выше порога, пайплайн возвращает `found = false` и не вызывает LLM. Порог подбирается на benchmark по запросам вне корпуса.

## Генерация

В LLM передаются: инструкция, пронумерованные фрагменты и вопрос пользователя. Требования инструкции:

- отвечать только по переданным фрагментам;
- после утверждения ставить номер фрагмента в квадратных скобках;
- если во фрагментах нет ответа — так и сказать;
- дозировки, граммы и калории приводить только те, что есть во фрагментах, без пересчёта и округления «от себя»;
- не давать медицинских рекомендаций, не отвечать о рецептурных препаратах, стероидах, гормонах и допинге, даже если вопрос сформулирован косвенно;
- не советовать экстремальные диеты и голодание.

Предупреждение о консультации с врачом LLM не пишет: его добавляет интерфейс, когда среди источников есть документы области `supplements`. Так оно не зависит от формулировки модели.

Для сценария «Программа» поисковый запрос собирается из параметров формы, а LLM возвращает программу в структурированном виде (JSON по схеме из `spec/tech/api.md`).

## Benchmark

Набор запросов в `benchmark/queries.json`:

```json
{
  "id": "q01",
  "topic": "training",
  "query": "сколько минут отдыхать между тяжёлыми подходами",
  "relevant": ["doc_012", "doc_013", "doc_047"]
}
```

Требования из задания:

- запросы равномерно покрывают темы корпуса: поровну на каждую из четырёх областей плюс несколько запросов на стыке областей;
- у каждого запроса не менее трёх релевантных документов;
- запросы сформулированы своими словами, а не скопированы из текста.

Метрики:

```
Recall@k = среднее по запросам от |R ∩ Top_k| / |R|
MRR      = среднее по запросам от 1 / rank первого релевантного документа
```

Считаем Recall@5, Recall@10 и MRR — по всему набору и отдельно по каждой области, чтобы видеть, где поиск слабее.

Отдельная группа запросов без релевантных документов (не по теме, о лечении, о запрещённых средствах) проверяет порог отказа: для них считаем долю запросов, на которые система ответила отказом. В Recall и MRR они не входят.

Результаты каждого прогона сохраняются в `benchmark/results/` с датой и параметрами.
