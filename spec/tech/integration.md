# RAG с GigaChat

Сервер использует `app/rag/pipeline.py` вместо демонстрационной заглушки.
Зависимости поиска устанавливаются из `requirements-rag.txt`; новых библиотек нет.
Профиль: `data/corpus-v4/profile.json`, корпус v4 (620 документов), индекс v4.
Модель по умолчанию — GigaChat-3-Ultra; `.env` может переопределить её.
Корпус содержит 599 прежних чанков и 21 практическую карточку проекта.
Происхождение новых текстов указано в manifest; отдельного режима ответа нет.
Исторические профили, корпуса и отчёты не перезаписываются.

При старте проверяются хеш корпуса, соответствие индекса текстам, параметрам
профиля и правилам понятий, а также хеш manifest с правилами поиска и каталогом.
Отсутствующий индекс можно восстановить в памяти
из этого же корпуса с теми же настройками. Несовместимый существующий индекс
вызывает ошибку конфигурации, а не скрытое переключение поиска.

Для вопроса выбираются пять чанков BM25, с приоритетом практической карточки
при совпадении шаблона базового вопроса. Для коротких вопросов до 100 символов
с таким совпадением в LLM передаются только совпавшие карточки из top-5.
Пустая выдача или лучший score <= 0 даёт отказ без обращения к LLM. Остальную
достаточность контекста оценивает модель. Это политика приложения, не новый
откалиброванный порог BM25. Явно запрещённые запросы
также отклоняются до генерации. Регулярные выражения не являются полным
классификатором: остальные ограничения повторяются в системном промпте.

Контекст и пользовательский ввод передаются как данные в JSON. Промпты
запрещают исполнять инструкции внутри них, использовать внешние знания,
назначать лечение и добавлять отсутствующие в источниках дозировки.
Явная блокировка содержания провайдером (`blocked`) в сценарии вопроса
возвращается как отказ без источников, а не техническая ошибка 502.
Сетевые ошибки, таймауты, квота и неверная структура по-прежнему являются ошибками.
Модель возвращает JSON с отдельными утверждениями и номерами предложений
из контекста (`evidence: [{source: 1, passages: [2,3]}]`). Предложения выделены
без изменения текста; цитаты по этим номерам извлекает сервер.
Сервер проверяет структуру, принадлежность каждой цитаты найденному чанку,
наличие чисел утверждения в его цитатах, сам назначает номера ссылок и
возвращает только использованные источники. Повторяющиеся ключи JSON запрещены.
При ошибке структуры или обоснования разрешена одна корректирующая генерация
с причиной отклонения и прежним JSON. Если повторный пересказ отклонён, но модель выбрала
существующие предложения, вопрос может получить `answer_type:extractive`:
дословные отрывки вместо неподтверждённого пересказа, с явным пояснением.
Номера предложений проверяются заново; максимум четыре отрывка, до 3200
символов. Это не применяется к программе. Невалидный JSON или ссылки без
проверяемых отрывков — 502; сетевые ошибки на этом уровне
не повторяются. URL берётся из manifest корпуса,
никогда из ответа модели. Некорректный ответ — ошибка 502, не «нет материала».
Эти проверки не доказывают научную корректность или логическое следование:
для этого остаётся смысловая проверка ответа вместе с источником.
Дополнительные консервативные проверки требуют сохранять предположение как
предположение, явно обозначать контекст исследовательских доз и не терять
условие отсутствия дефицита калорий при цитировании связанной числовой нормы.
Это адресные эвристики по найденным сбоям, не универсальный семантический контроль.

Программа отбирает карточки из того же корпуса по метаданным цели, уровня и
оборудования. Доступно 18 упражнений, шесть схем нагрузки и расписания на 2–5
дней. LLM выбирает идентификаторы упражнений; сервер проверяет число дней,
двигательные группы, отсутствие повторов и допустимое оборудование, затем
подставляет названия, подходы, повторения и ссылки из карточек. Некорректный
выбор LLM заменяется проверенной базовой схемой из того же каталога.
Ошибка провайдера не скрывается шаблоном. Если подходящих карточек нет,
возвращаются `found:false`, пустые `days` и `sources`, объяснение в `note`.
Это учебный шаблон для здорового взрослого, не медицинское назначение.
Лимит генерации программы — 3000 токенов на попытку; вопрос использует лимит
из `.env`. Клиент допускает явный `max_tokens` для конкретного вызова.

Устройство памяток и воспроизводимая сборка — [practical-corpus.md](practical-corpus.md).
Старая проблема отказа на «Нужен ли креатин?» исправлена в v4; короткие вопросы
проверяются живым набором `scripts/rag_smoke.py --suite basic`.
Это не заменяет независимую оценку качества генерации.

API сохраняет прежние поля; источники дополнены `url`, `section`, `quotes`.
У вопроса с ответом поле `answer_type` равно `generated` или `extractive`.
У каждого упражнения добавлено `citations` (массив номеров источников).
У программы добавлено `found`. UI показывает ссылки у упражнений, выделяет
дословные цитаты в исходном чанке, открывает оригинал, скрывает демо-плашку.
При новом запросе старый результат скрывается, поле ввода сохраняется.

LLM создаётся лениво, ошибки конфигурации возвращаются через API без секретов.
`health` сообщает только о готовности локального поиска, не проверяет API-ключ.
Проверки unittest используют настоящий поиск и подменённую генерацию;
живые вызовы выполняются отдельно, с сохранением ответов и цитат.

Изменяемые файлы старого интерфейса/API сохранены побайтно в
`benchmark/history/pre-gigachat/`. Старые снимки хешей описывают версию ДО
интеграции: проверка полного старого дерева требует этих архивных файлов.
Исторические версии сохранены; отдельный аудит новой выдачи находится в
`benchmark/practical-v4/`. В формулах BM25 и параметрах k1/b изменений нет.
