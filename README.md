# gym-coach-rag

RAG-ассистент персонального тренера: отвечает на вопросы о тренировках в зале, питании, спортивных добавках и восстановлении и составляет программы тренировок — со ссылками на источники.

Учебный проект курса «НИРС 2026: разработка RAG-приложения с помощью LLM» (МГТУ им. Н. Э. Баумана).

## Состояние

Контрольная точка 2: единый корпус v4 — 599 научных чанков и 21 практическая карточка проекта, всего 620 документов. GigaChat-3-Ultra отвечает с источниками и выбирает упражнения для программы; сервер проверяет программу и берёт числовые параметры из карточек. Собственный BM25 сохранён. Полная смысловая вычитка прежнего перевода ещё не завершена; устройство и ограничения — в [описании интеграции](spec/tech/integration.md).

## Запуск

Нужен Python 3.11+, зависимости поиска и настроенный `.env` с ключом GigaChat:

```bash
python3 -m venv venv/rag
venv/rag/bin/python -m pip install -r requirements-rag.txt
venv/rag/bin/python -m app
```

Интерфейс откроется на http://127.0.0.1:8000. Порт и адрес меняются флагами `--port` и `--host`.

## GigaChat

Подготовлен `app/llm.py`: авторизация, обновление токена, генерация и ошибки.
[Как бесплатно получить ключ и настроить .env](spec/tech/gigachat.md).
В текущей рабочей копии ключ и сертификат настроены локально и исключены из Git.
Для нового клонирования используйте `.env.example` и инструкцию по сертификату.

После заполнения Authorization key:

```bash
venv/rag/bin/python -m app.llm --check
venv/rag/bin/python -m app.llm --smoke
```

Первая команда проверяет доступ без генерации, вторая расходует небольшую квоту.
Отдельная проверка настоящего API и ответов с источниками (расходует квоту):

```bash
venv/rag/bin/python scripts/rag_smoke.py --live --output /tmp/gigachat-smoke-new.json
```

Существующий отчёт не перезаписывается. Это smoke-проверка, не оценка качества
на независимом наборе. Дополнительные наборы: `--suite basic` (четыре коротких
вопроса и пятидневная программа) и `--suite refusals` (12 отказных вопросов).

## Автономный поиск BM25

После установки `requirements-rag.txt`:

```bash
venv/rag/bin/python -m app.rag.build_index
venv/rag/bin/python -m benchmark.run
```

Индекс сохраняется в `data/index/bm25.json` (исключён из Git). Для экспериментов
доступны `--k1`, `--b`, `--no-lemmatize`, `--keep-stopwords`. При изменении
корпуса или правил предобработки пересоберите индекс.

Пример из Python, запущенного в корне проекта:

```python
from app.rag.bm25 import BM25Index

index = BM25Index.load("data/index/bm25.json")
for result in index.search("Помогает ли креатин увеличивать силу?", k=5):
    print(result.doc_id, result.score)
```

Текст и метаданные находятся по `doc_id` в `data/corpus/documents.json`,
ссылки на оригиналы — в `data/corpus/manifest.json`. Оценка BM25 — число для
ранжирования, не вероятность правильного ответа. Проведён подбор 120 конфигураций (`python -m benchmark.tune`): лемматизация,
сохранение стоп-слов, k1=3, b=0. Recall@5: 0.2029 → 0.2436,
Recall@10: 0.3188 → 0.3470, MRR: 0.7382 → 0.7361. Профиль и порог
13.909689866544728 сохранены в `benchmark/selected_config.json`, отдельный индекс —
`data/index/bm25.tuned.json`. Это подбор на development-наборе, не независимая
итоговая оценка. Дополнительно создан новый holdout (24+12 вопросов):
на нём исходный → выбранный профиль даёт Recall@5 0.3761 → 0.3770,
Recall@10 0.4925 → 0.5079, MRR 0.6172 → 0.6638. Подробности —
в [описании holdout](benchmark/holdout/README.md). После аудита всех top-10 обоих профилей
сохранена [разметка v2](benchmark/holdout-v2/README.md): для выбранного профиля
Recall@5 0.4081, Recall@10 0.5985, MRR 0.7666. Это уточнение разметки
при неизменном поиске; первый отчёт сохранён. Методика, проверка на трёх разбиениях и ограничения —
в [benchmark/README.md](benchmark/README.md). Это исторический профиль;
результаты этого этапа сохранены; текущий сервер использует корпус v4.

## Исправленный корпус и автономный поиск v3

Новая версия корпуса: `data/corpus-v3/documents.json` — 599 чанков, 21 перевод
исправлен по оригиналам. Старый корпус сохранён для воспроизводимости.
Текущий автономный кандидат использует общие понятия периодизации, суперсетов,
холодного погружения и заминки. Полная вычитка корпуса ещё не завершена.

```bash
venv/rag/bin/python -m app.rag.retrieval build --corpus data/corpus-v3/documents.json --output data/index/bm25.v3.json --variant concepts
venv/rag/bin/python -m app.rag.retrieval search --index data/index/bm25.v3.json --query 'Нужна ли периодизация тренировок?' --k 5
```

Диагностический v2 → v3: Recall@5 40.81% → 48.73%, Recall@10 59.85% → 71.83%,
MRR 0.767 → 0.869. На development Recall@10 снизился с 34.70% до 34.33%.
Это исправление известных ошибок, не новая независимая оценка; остаются
ограничения полноты разметки вне проверенного пула.
[Подробности четырёх сравнений v3](benchmark/retrieval-v3/README.md).

Последующая [разметка v3.1](benchmark/retrieval-v3.1/README.md) закрыла 8 попаданий
и пересмотрела одну метку дневного сна. При неизменном поиске R5=49.22%,
R10=72.03%, MRR=0.869; весь выбранный диагностический top-10 размечен.
Порог v3 откалиброван на development: 13.909689866544728. Отдельный профиль —
`benchmark/retrieval-v3.1/selected_config.json`; 10/12 правильных и 1/24 ложных
отказов на diagnostic, а на трёх отложенных частях development — 9/12 и 2/24.
Этот профиль подключён к серверу; алгоритм поиска и старые отчёты при интеграции не менялись.

## Основной сценарий

1. Пользователь задаёт вопрос о тренировках, питании, добавках или восстановлении.
2. Система находит в корпусе релевантные фрагменты (BM25).
3. LLM формирует ответ только по найденным фрагментам.
4. Пользователь видит ответ и пронумерованные источники, на которые он опирается.

Второй сценарий — составление программы тренировок по параметрам (цель, уровень, число дней, оборудование). Подробнее: [spec/product/scenarios.md](spec/product/scenarios.md).
